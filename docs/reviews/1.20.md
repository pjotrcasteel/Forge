# Forge 1.20 review — composite topology evolution

## Capability

Applications can compose multiple independently reconciled topology components into one typed transition, validate cross-topology invariants, and derive one dependency order for the resulting operations.

## Strong typing

The application defines `TContext`, `TOperation`, `TKey`, and `TViolation`. A context can contain concrete `TopologySyncPlan<...>` instances for services, resources, ownership, or other domains without Forge flattening them into strings or `object`.

## SOLID boundary

Each cross-topology rule implements the narrow `ICompositeTopologyInvariant<TContext, TViolation>` interface. New invariants are added by the consumer without modifying Forge.

## Safety and complexity

Operation keys and dependency endpoints are validated before planning. Invariants run before the plan is considered valid. Dependency ordering remains O(V + E); invariant cost is explicitly consumer-owned. No execution, transport, persistence, or authorization logic moved into Forge.
