# Milestone 0.14 review — nested reconciliation

## Goal

Let aggregate-like parent models expose meaningful child add/update/remove plans instead of flattening a child collection into one scalar changed flag.

## What changed

A parent generated Sync model can explicitly mark a child collection:

```csharp
[GenerateSync(nameof(Service.Id))]
public sealed record Service(
    string Id,
    [property: SyncNested]
    IReadOnlyList<Characteristic> Characteristics);
```

The child type must itself use `GenerateSync`.

The generated parent synchronizer:

- excludes the nested collection from the parent Delta;
- includes child reconciliation when deciding whether the parent is updated;
- generates `PlanCharacteristics(current, desired)`;
- generates `PlanCharacteristics(parentUpdate)` for convenient drill-down;
- supports `SyncNested(SyncMode.Upsert)` when the child collection is explicitly partial.

## Dogfood result

A changed RFS can now be represented as:

```text
RFS subnet
  Updated

  Characteristics
    Updated
      ipSubnet
        Value: 10.1.0.0/24 -> 10.2.0.0/24
```

The parent `ResourceFacingServiceDelta` remains focused on direct parent state. Child collection reconciliation remains a Sync concern.

## Alignment review

This is intentionally opt-in. Forge does not inspect arbitrary collections and guess that they are aggregate boundaries. The explicit annotation carries structural reconciliation intent while application orchestration remains outside Forge.

The current implementation computes child plans during parent classification. 0.17 should benchmark this and add a cheaper no-allocation nested change check if measurement shows it matters.

## Decision

Proceed. Configuration now needs to become richer and more consistent across directly annotated and profile-generated models.
