# Forge 1.1-1.8 feature train review

## Goal

The feature train deliberately stops treating CI, packaging and documentation polish as product milestones. Every release adds a planning capability that solves a new class of state-transition problem.

## 1.1 — Explainable plans

`SyncPlanExplainer` converts same-type and cross-type plans into a structured explanation model. Delta paths become nested reasons and applications can add dependency, prerequisite, policy or execution facts through `PlanExplanationBuilder<TKey>`.

## 1.2 — Generated cross-type profiles

`[GenerateCrossSyncProfile]`, `[CrossSyncIdentity]` and `[CrossSyncMap]` generate reflection-free cross-type reconciliation for the common layered-model case. Advanced heterogeneous identity matching remains available through `CrossSyncMatchDefinition`.

## 1.3 — Operation rules

`SyncOperationRules` and `CrossSyncOperationRules` evaluate ordered Delta-aware rules. The first matching update rule wins and the selected rule is attached to the plan explanation.

## 1.4 — Incremental replanning

`IncrementalReplanner` tracks application-owned operation IDs across replans. IDs survive only when the canonical single-operation manifest digest is unchanged. Results distinguish retained, newly required, no-longer-required and semantically replaced operations.

## 1.5 — Impact analysis

`ImpactAnalyzer` performs deterministic breadth-first propagation over application-supplied graph edges. It returns direct impact, transitive impact and one shortest reason path to every affected logical item.

## 1.6 — Plan constraints

`PlanConstraintSet<TPlan>` validates a complete proposal before execution and returns all violations. Sync conveniences cover maximum change count, removal prohibition and protected keys; dependency plans can be constrained to acyclic state.

## 1.7 — Conflict resolution

`MergeResolver` turns generated three-way analysis into an explicit semantic patch. Non-conflicting branch changes combine automatically. Conflicts can prefer current, desired, baseline or application-owned custom values, while missing policy stays unresolved.

## 1.8 — Plan simulation

`ManifestPlanSimulator` applies a portable plan to a portable current-state snapshot only when stale-plan preconditions still hold. The projected state can be compared with an expected target without executing infrastructure code.

## Combined flow

```text
Current state + desired state
          |
          v
Delta / Sync / CrossSync
          |
          +--> Explanation
          |
          +--> Operation rules
          |
          +--> Impact analysis
          |
          +--> Constraints
          |
          +--> Incremental replanning
          |
          +--> Portable manifest
          |
          +--> Stale-plan validation
          |
          +--> Simulation
          |
          v
Application-owned execution
```

Three-way concurrency is a parallel path:

```text
baseline + current + desired
          |
          v
AnalyzeMerge
          |
          v
MergeResolutionPolicy
          |
          v
semantic merge patch
```

## Architecture check

The feature train keeps the original Forge boundary intact:

- no persistence;
- no transports;
- no DI requirement;
- no hidden I/O;
- no workflow engine;
- no domain-specific operation names;
- no reflection in generated normal execution paths.

Forge calculates, explains, validates, replans and simulates. The consuming application still owns business meaning and side effects.

## Validation status

Static release validation passes for XML/JSON/YAML parsing, project references, source structure, line length, public API snapshot ordering, version alignment, domain leakage and package-verifier syntax.

A .NET SDK is not available in this execution environment, so the real `dotnet build`, `dotnet test`, `dotnet pack`, Native AOT and package-consumer gates remain CI responsibilities and are not claimed as executed here.
